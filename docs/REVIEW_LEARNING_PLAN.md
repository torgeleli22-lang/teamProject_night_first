# 개발 계획서 — 검토 경험으로 배우는 검토 AI

- 상태: **1단계 구현 (v3.3)** · 2~4단계 계획 (2026-11-12)
- 목적: 검토 AI 의 **판정 오류**(쓸 수 있는 코드를 버림)와 **추적 실수**(두 검토의 실행 결과가 갈림)를 줄여, AI 비용을 아끼고 AI 문항 제공률을 높인다. **틀린 코드를 통과시키는 쪽으로는 배우지 않는다.**
- 기준 문서: `docs/GENERATION_STANDARD.md` 8.1 · DB 항목: `docs/LAMBDA_STRUCTURE.md`

---

## 1. 배경 (실험 v3.2, 42문항)

| 근거 | 내용 |
|---|---|
| 버린 문항의 비용 | 예시 코드로 바뀐 4문항에 쓴 AI 비용 $0.58 = 전체 $2.22 의 26% |
| 버린 이유 | 두 검토의 출력 불일치 3 (정렬 순서 · 등급 경계값 · 시간대 요금 계산) · 검토 답 잘림 후 "의도와 다른 동작" 지적 1 |
| 검토가 갈린 시도를 실제로 실행 | 8회 중 검토 1 이 맞음 1 · 검토 2 가 맞음 5 · 생성 AI 예상 출력이 맞음 2 |
| 지금의 학습 | 생성 AI 에게만, 고정된 조언 문장 6개 중에서 (`history.py`). 검토 AI 는 아무것도 배우지 않음 |

## 2. 정해진 기준

| 항목 | 결정 |
|---|---|
| 의도와 다른 동작 | 이름·주석·출력 문구가 말하는 의도와 실제 동작이 다르면 **문제**(진짜 오류)로 본다 — 학습자를 헷갈리게 하므로. 실행 설명을 잘못 적은 것(기록 실수)은 문제가 아니다 |
| 정답의 출처 | **실제 실행만** 정답으로 쓴다. AI 가 AI 를 판정한 결과는 정답으로 쓰지 않는다 |
| 실행 위치 | **실행 전용 Lambda (추후 추가)**. 지금의 Lambda 3개(`jojo_auth`·`jojo_practice`·`jojo_review`)는 코드를 실행하지 않는다 |
| 통과 규칙 | 경험·모델이 무엇을 말해도 **두 검토의 출력이 같아야 제공**한다 (다수결 없음, v3.0) |

## 3. 전체 흐름

```
[jojo_practice]  생성 → 규칙 검사 → 검토 1 → 규칙 검사 2 → 검토 2 → 출력 판정
                      │ 버린 시도 (동작 문제 · 두 검토 불일치)
                      ▼
   CASE#<언어>#<난이도>  label=pending  (코드 · 검토 의견 · 두 출력 · 코드 특징)          ← 1단계 (구현됨)
                      ▼
[jojo_runner (추후)]  pending 사례를 격리 실행 → 정답 라벨                                  ← 2단계
   false_alarm (판정 오류) · real_error (진짜 오류) · trace_slip (추적 실수) · unknown
                      ▼
   EXPERIENCE#<언어>  (kind · 검토 의견 · 실제 · 교훈 · 코드 특징)
                      ▼
[jojo_practice]  검토 1·2 프롬프트에 비슷한 경험 최대 3개                                   ← 1단계 (구현됨, 경험이 생기면 동작)
                 오판 분류 모델 → 버리기 전 재심 1회                                        ← 3단계
```

## 4. 단계별 계획

### 1단계 — 사례 기록 + 경험 보여 주기 (v3.3, 구현됨)
| 무엇 | 어디 |
|---|---|
| 시도마다 검토한 코드를 단계 기록에 남김 (`step.code`) | `generate.make_code` |
| 코드 특징 (AI 없음): 줄 · 함수 · 반복문 · 중첩 반복 · 분기 · 정렬 · 등호 비교 · 나눗셈 | `experience.code_features` |
| 모든 시도의 분류 + 코드 특징 → `GENLOG#` (실패 예측 모델의 학습 데이터) | `history.record_generation` |
| 버린 시도(`not_runnable` · `disagree`)의 사례 → `CASE#<언어>#<난이도>` / `<시각>#<시도>`, `label=pending`, 180일 | `experience.record_cases` |
| 검증된 경험이 있으면 검토 1·2 의 사용자 메시지 끝에 최대 3개 (같은 난이도 +2, 같은 특징마다 +1, 같은 종류 2개까지) | `experience.review_experiences` |
| 끄기 | `REVIEW_EXPERIENCE=off` |
| 의도와 다른 동작도 문제 (검토 프롬프트) | `generate.REVIEW_PROMPT` |

### 2단계 — 실행 전용 Lambda 로 정답 붙이기 (계획)
**함수**: `jojo_runner` — 런타임 Python 3.14 + Node.js 계층(또는 컨테이너 이미지), **IAM 권한 없음**(DynamoDB 접근도 없음), VPC 없음, 함수 URL 없음.
- 부르는 쪽: 관리자 감사 스크립트(CloudShell) 또는 `jojo_practice` 의 예약 실행(EventBridge Scheduler). 사례를 읽고 결과를 쓰는 것은 부르는 쪽이 하고, `jojo_runner` 는 **코드를 받아 실행 결과만 돌려준다** (자격 증명이 없으니 코드가 무엇을 해도 AWS 자원에 닿지 못함)
- 입력 `{language, code}` → 출력 `{exitCode, stdout, stderr, timedOut, runs: 2}`

**격리 실행 규칙**
| 항목 | 값 |
|---|---|
| 시간 | 실행 1회 3초, 두 번 실행해 출력이 다르면 `unknown` (랜덤·시각) |
| 메모리·출력 | 128MB 자식 프로세스(`resource.setrlimit`), 출력 64KB 까지 |
| 입력 | 표준 입력은 빈 값 (입력을 기다리면 오류 → `unknown`) |
| 환경 | 자식 프로세스 환경 변수 비움, 작업 폴더는 `/tmp` 의 새 폴더, 끝나면 지움 |
| 네트워크 | VPC 없는 Lambda 는 밖으로 나갈 수 있음 → 실행 전 정적 검사로 `socket`·`urllib`·`http`·`fetch`·`require('http')` 등을 쓰는 코드는 실행하지 않고 `unknown` |

**라벨 규칙**
| 사례 | 실제 실행 | 라벨 |
|---|---|---|
| 동작 문제로 버림 | 실제로 오류(예외·시간 초과) | `real_error` |
| 동작 문제로 버림 | 오류 없이 실행되고, 검토가 지적한 것이 "의도와 다른 동작"(이름·출력 문구와 실제 결과가 다름) | `real_error` (2장 기준) |
| 동작 문제로 버림 | 오류 없이 실행되고, 지적이 실행 결과와 맞지 않음 | `false_alarm` |
| 두 검토 불일치 | 실제 출력 = 한쪽 검토 | `trace_slip` (틀린 쪽 · 갈린 줄 · 코드 특징 기록) |
| 두 검토 불일치 | 실제 출력이 둘 다와 다름 | `trace_slip` (둘 다 틀림 — 생성 쪽 교훈) |
| 실행할 수 없음 · 실행마다 다름 | — | `unknown` (경험으로 쓰지 않음) |
- "의도와 다른 동작" 여부는 실행만으로 정할 수 없어 **사람 확인**(관리자)으로 정한다. 확인 전에는 경험으로 쓰지 않는다
- 경험 문장(`claim` · `truth` · `lesson`)은 규칙으로 만든다 (예: "정렬 기준이 같은 값의 순서를 다르게 따라감 → 실제는 원래 순서 유지(안정 정렬)"). AI 로 요약하면 비용·오류가 생겨서 쓰지 않는다

### 3단계 — 오판 분류 모델 + 재심 (계획)
- **입력 특징**: 검토 의견 문장에 실제 오류 낱말(NameError·0 으로 나누기·범위·무한 반복)이 있는지, 실행 설명 문장("…가 실행되어", "실제 출력은")인지, `runnable=true` 와 문제를 함께 적었는지, 규칙 검사 1 통과, 언어·난이도, 코드 특징
- **정답**: 2단계 라벨 (`false_alarm` vs `real_error`). 100~200건이 쌓이면 시작
- **모델**: 로지스틱 회귀 (CloudShell 에서 scikit-learn 으로 학습 → **가중치 숫자만** `jojo_practice` 에 넣음. Lambda 라이브러리는 늘리지 않음)
- **쓰임**: 오판 확률이 높으면 버리기 전에 **재심 1회**(검토에게 "이 지적이 실행 오류·의도와 다른 동작인지" 다시 묻기). 재심도 문제라고 하면 지금처럼 버린다. **모델이 직접 통과시키지는 않는다**
- 같은 방식으로 **실패 예측 모델**(코드 특징 → 두 검토가 갈릴 확률)도 만든다. 단, 개념 특징(증감·반복·정렬 같은 가르칠 내용)은 판단에 쓰지 않고 모호함 특징(정렬 값 겹침·경계값과 같은 데이터)만 쓴다. 위험하면 버리지 않고 "개념은 유지하고 데이터만 바꿔" 재생성하거나 검증을 한 번 더 한다

### 4단계 — 효과 측정과 확장 (계획)
- 실험 옵션: `REVIEW_EXPERIENCE` 켬/끔, 같은 `--seed` 로 비교
- 지표: 판정 오류로 버린 비율 · 두 검토 불일치 비율 · 예시 코드 대체율 · **제공 문항 출력 정확도(떨어지면 안 됨)** · 문항당 비용 · **개념별 생성 비율(줄면 안 됨)**
- 경험이 수천 건 쌓이고 모델·리전이 지원하면 검토 모델 파인튜닝·증류를 검토한다

## 5. 위험과 대응

| 위험 | 대응 |
|---|---|
| 틀린 코드를 통과시키도록 배움 | 정답은 실제 실행만 · 통과 규칙(두 검토 일치)은 그대로 · 모델은 재심만 정함 · `real_error` 경험도 함께 보여 줌 |
| 어려운 개념을 피하게 됨 | 개념 특징은 판단에 쓰지 않음 · 개념별 생성 비율을 실험표에 넣어 지켜봄 |
| AI 가 만든 코드를 실행하는 보안 위험 | 권한 없는 별도 Lambda · 자격 증명·환경 변수 없음 · 시간·메모리 제한 · 네트워크 쓰는 코드는 실행하지 않음 |
| 프롬프트가 길어져 비용 증가 | 경험 최대 3개, 문장은 짧게 (경험 하나 300자 이하) |
| 사례에 코드 원문 저장 | 코드는 AI 가 만든 것(학습자 글 아님) · 180일 뒤 자동 삭제 · 관리자만 읽음 |
