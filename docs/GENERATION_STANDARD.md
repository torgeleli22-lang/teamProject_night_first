# 연습 코드 생성·검증 기준 (v2)

AI 가 만든 코드가 **무엇을 갖춰야 학습자에게 내보낼 수 있는지**, 그리고 **채점 기준을 무엇으로 정하는지**를 정하는 문서예요.
코드(`lambda/jojo_practice/`)의 프롬프트·규칙 검사는 이 문서를 따르고, 기준을 바꿀 때는 이 문서부터 고쳐요.

- 상태: **v2.7** (2026-11-08) — 변경은 맨 아래 `변경 기록`
- 목적: 정답 값을 맞히는 곳이 아니라 **학습자가 코드의 흐름을 이해하고 설명할 수 있게** 연습시키는 곳이에요
- 원칙
  - 난이도는 **코드 길이나 문법 개수가 아니라 6가지 요소**로 정해요 (1장)
  - 생성과 검증을 나눠요: **생성 AI(Haiku)가 코드와 예상 출력**을 내고, **검토 AI 두 개**가 각자 따로 따라가요 — 검토 1 은 GPT-5.6 Luna, 검토 2 는 초급·중급 Claude Haiku · **고급 Luna 한 번 더** (모두 Bedrock)
  - **출력으로 판정해요.** 두 검토가 같으면 제공, 다르면 생성 AI 의 예상 출력까지 **3개를 비교해 2:1 이면 2 쪽으로 정해 제공**, 셋 다 다르면 다시 만들어요
  - 정해진 출력은 학습자에게도 보여 줘요. 목적은 값을 맞히는 게 아니라 **코드를 이해하고 흐름을 설명하는 것**이라, 결과를 보며 "왜 이렇게 나오는지"를 설명하게 해요
  - 검토 AI 가 실제로 실행하듯 따라간 기록은 버리지 않고 **채점 기준으로 저장**해요
  - 모듈·랜덤·시각·입력 등 **언어 기능은 금지하지 않아요**. 값이 정해지지 않는 곳은 검토 AI 가 값을 정하고 "가정"으로 표시해요
  - 서버는 코드를 실행하지 않아요. 검토는 AI 가 실행을 따라가는 시뮬레이션이라, **서로 다른 두 AI 의 기록이 맞는지**로 확인해요 (두 AI 가 똑같이 틀리면 못 잡는 한계가 있어요)

## 0. 흐름

```
학습자: 언어(Python·JavaScript) · 난이도(초급·중급·고급) · 주제(랜덤 또는 직접 입력)
① 생성 AI   (code_generation, Claude Haiku 4.5, 온도 0.5)  난이도 기준(6요소)을 그대로 받아 코드 + 예상 출력을 만든다
   → 규칙 검사 1 (AI 없음)     문법 오류 · 빈 코드 · 너무 긴 코드(300줄)
② 검토 AI 1 (code_review, GPT-5.6 Luna)      코드를 실행하듯 따라간다 → 실행 기록 · 출력 · 동작 판정 · 난이도 판정(6요소) · 흐름 단위별 모범 설명
   → 규칙 검사 2 (AI 없음)     실행 기록이 코드의 함수·반복문을 빠짐없이 다뤘는지 · 모범 설명이 있는지 · 손으로 따라갈 크기
③ 검토 AI 2 (trace_check, 초급·중급 Claude Haiku 4.5 · 고급 GPT-5.6 Luna)   검토 1 의 기록을 보지 않고 같은 코드를 따로 따라간다 → 출력 (가정한 값은 검토 1 과 같게)
   → 출력 비교 (AI 없음, 4.1)   검토 1 = 검토 2 → 통과
                                 다르면 생성 AI 의 예상 출력까지 3개: 2:1 → 2 쪽 출력으로 정함 · 셋 다 다름 → ① 다시
④ 통과        화면에는 코드 · '설명할 곳(※)' 줄 범위 · **정해진 출력**. 실행 기록·모범 설명은 저장해 두고 채점에만
   걸리면     코드 문제 → 부분 수정(바꿀 줄만) 1번 → ② 다시 / 난이도 불일치 → 검토 의견을 붙여 ① 다시 1번 / 그래도 안 되면 준비된 예시 코드
```
- 문항당 AI 호출: 보통 **3번**(생성·검토 1·검토 2), 최대 **8번** (`MAX_CALLS`)

## 1. 난이도 6요소

| 요소 | 무엇을 보나 |
|---|---|
| ① 문법 복잡도 | 변수·자료형·연산자 같은 기본 문법부터 조건문·반복문·함수·클래스까지 어느 수준의 문법을 쓰는지 |
| ② 코드 구조 | 단순한 순차 구조인지, 여러 구문이 결합되거나 중첩된 구조인지 |
| ③ 논리적 복잡도 | 단순한 연산·조건 판단인지, 여러 조건을 조합하거나 복합적인 추론이 필요한지 |
| ④ 데이터 처리 | 단일 변수·기본 자료형인지, 리스트·배열·딕셔너리 같은 자료구조나 여러 데이터 사이의 관계를 다루는지 |
| ⑤ 실행 흐름 | 순차 실행인지, 분기·반복·함수 호출과 반환이 섞인 흐름인지 |
| ⑥ 개념 간 연계 | 하나의 개념 중심인지, 여러 개념(조건+반복, 함수+자료구조 …)을 결합하는지 |

| **초급** | 프로그래밍을 처음 배우는 사람 | 변수·자료형·기본 연산자 중심 · **하나의 핵심 개념** · 실행 순서와 결과가 쉽게 보이게 · 복잡한 조건·중첩 최소화 · 불필요한 함수·클래스·외부 라이브러리 지양 |

## 3. 생성 AI 에게 주는 규칙 (프롬프트)
1. 지정한 난이도가 우선 기준이다. 같은 주제도 난이도에 따라 문법·구조·논리 복잡도를 다르게 한다
2. 그 난이도에 맞는 개념을 쓴다. 초급은 기본 문법 중심, 중급·고급은 개념을 점진적으로 결합한다
3. 주제와 관계없는 문법·기능을 덧붙이지 않는다. 특정 문법을 배우는 코드라면 그 문법이 핵심 역할을 하게 한다
4. **코드 길이는 난이도 기준이 아니다.** 짧아도 논리가 복잡하면 높은 난이도, 길어도 단순 반복이면 낮은 난이도다
5. 명확한 변수명과 일관된 구조. 난이도를 높이려고 일부러 읽기 어렵게 만들지 않는다
6. 실행 결과를 볼 수 있게 출력(print · console.log)을 넣는다
7. **손으로 따라갈 수 있는 크기로 만든다.** 학습자가 종이에 값을 적어 가며 끝까지 따라갈 수 있어야 해요. 데이터 개수·반복 횟수·출력 줄을 아래 안으로.
   여러 단계를 거치는 시뮬레이션(시간·차례를 여러 번 돌리는 것)은 단계 수를 줄이고, 같은 모양의 출력을 반복해서 찍지 않는다
- 언어마다 문법은 달라도 판단 기준은 같다 (Python · JavaScript)

### 3.1 손으로 따라갈 크기 (`levels.TRACE_SIZE`)
| 난이도 | 반복문 하나가 도는 횟수 | 출력 줄 | 규칙 검사 2 가 걸러 내는 선 (여유를 둔 값) |
|---|---|---|---|
| 초급 | 5번 이하 | 10줄 이하 | 반복 10번 초과 · 출력 15줄 초과 |
| 중급 | 8번 이하 | 20줄 이하 | 반복 16번 초과 · 출력 30줄 초과 |
| 고급 | 10번 이하 (중첩이면 안쪽까지 합쳐 30번 이하) | 30줄 이하 | 반복 30번 초과 · 출력 45줄 초과 |

- 코드 길이(줄 수)는 여전히 난이도 기준이 아니에요. 이 값은 **따라가야 하는 양**의 한도예요
- 왼쪽은 생성 AI 에게 주는 기준, 오른쪽은 검토 기록(실제 반복 횟수 `count` · 따라간 출력 `output`)으로 확인하는 선이에요. 살짝 넘은 것까지 버리지 않게 여유를 둬요
- 이유: 실험(v2.1)에서 검토 AI 가 틀린 곳은 8분 × 놀이기구 3개를 매분 출력하는 긴 시뮬레이션이었어요. 학습자에게도 지나치게 길고, 검토 기록(채점 기준)도 틀리기 쉬워요

## 4. 검토 AI 가 하는 일 (② `code_review`)

코드를 **실제로 실행하듯 따라가며** 동작하는지 확인하고, 그 기록을 남겨요.

| 대상 | 하는 일 |
|---|---|
| 변수 | 코드에 정해진 값으로 따라가요 |
| 함수 | 매개변수에 값을 정해 넣고 실행하듯 따라가요 (호출하는 곳이 있으면 그 값으로) |
| 반복문 | 실제로 몇 번 도는지, 언제 멈추는지 확인해요 |
| 재귀 | 끝나는 조건(기저 조건)에 도달하는지, 반환값이 어떻게 쌓이는지 확인해요 |
| 값이 정해지지 않는 곳 | 랜덤·현재 시각·입력·외부 데이터는 값을 하나 정하고 `가정` 으로 표시해요 |

답 (`ReviewAnswer`)
- `units` — **흐름 단위**(함수 · 반복문 · 조건 분기 · 재귀 · 처리 덩어리)마다:
  줄 범위, 종류, `inputs`(넣은 값·가정), `steps`(값이 바뀌는 과정), `result`(나간 값·반환값), `count`(반복·재귀 횟수), `stop`(멈춘 조건),
  `explanation`(그 기록으로 쓴 **흐름 중심 모범 설명** 2~3문장), `keywords`(설명 속 핵심 표현), `key`(학습자가 꼭 설명해 볼 곳인지)
- `output` — 따라간 대로라면 출력되는 줄
- `runnable` · `problems` — 실제로 동작하는 코드인지, 아니면 "몇 번째 줄: 무엇이 왜"
- `level` — 6요소마다 판단한 난이도와 이유, 종합 난이도, 요청한 난이도와 맞는지(`match`), 맞추려면 무엇을 바꿀지(`advice`)

모범 설명 기준: **흐름 중심** — 무엇이 들어와 → 어떤 조건·반복을 거쳐 → 무엇이 남는지. 값은 흐름을 보여 주는 근거로 써요 (가정한 값이면 가정이라고 밝혀요). 2~3문장, 300자 이하, 한국어 존댓말 "~해요".

## 4.1 출력으로 판정하기 (② 검토 1 · ③ 검토 2 · ① 예상 출력)
| 무엇 | 기준 |
|---|---|
| 세 의견 | ① 생성 AI 의 **예상 출력** (코드와 함께 씀, 부분 수정으로 코드가 바뀌면 쓰지 않음) · ② 검토 1(Luna)의 출력 · ③ 검토 2의 출력 (초급·중급 Haiku · 고급 Luna — 검토 1 과 따로 새로 부름) |
| 고급의 검토 2 | 고급은 계산·조건이 얽혀 Haiku 가 자주 놓쳤어요 (v2.6 실험: 검토가 갈린 고급 시도 5개 중 Haiku 가 맞은 것 0). 그래서 고급은 Luna 를 한 번 더 따로 불러 검토 2 로 써요. 같은 모델이라 같은 실수를 할 수 있어서, 생성 AI 의 예상 출력(Haiku)이 세 번째 의견으로 남아요. 환경 변수 `CHECK_MODEL_ID_HIGH` 로 바꿀 수 있어요 |
| 검토 2 에게 주는 것 | 코드(줄 번호) · 검토 1 이 정한 **가정 값**(랜덤·시각·입력). 검토 1 의 기록(값·출력)은 주지 않아요 |
| 같다고 보는 것 | 출력 줄이 순서대로 모두 같음. 표시만 다른 것은 같다고 봐요: 띄어쓰기·빈 줄 · 따옴표 · 괄호(`['a', 'b']` = `a,b`) · `4.0` = `4`. 반복 횟수는 기록에만 남기고 판정에는 쓰지 않아요 (두 AI 가 구간을 다르게 세는 일이 잦았음) |
| ② = ③ | 통과 — 그 출력으로 제공 |
| ② ≠ ③ 이고 ① = ② | 2:1 로 검토 1 의 출력 — 검토 1 의 기록 그대로 제공 |
| ② ≠ ③ 이고 ① = ③ | 2:1 로 검토 2 의 출력 — 검토 1 에게 정해진 출력을 알려 주고 기록(실행 기록·모범 설명)을 다시 쓰게 함. 다시 쓴 출력이 정해진 출력과 같으면 제공, 아니면 ① 다시 (채점 기준이 정해진 출력과 어긋난 채 나가지 않게) |
| 셋 다 다름 · 예상 출력이 없음 | ① 다시 ("따라가기 쉽게, 결과가 하나로 분명히 정해지게") → 끝내 안 되면 예시 코드 |
| 검토 2 를 쓸 수 없음 | 판정하지 못한 코드는 내보내지 않아요 (① 다시 / 예시 코드) |
| 화면 | 정해진 출력을 읽기 화면에 '실행 결과'로 보여 줘요 |

## 5. 규칙 검사 (AI 없음, 비용 0)

| 단계 | 규칙 | 걸리면 |
|---|---|---|
| 1 (생성 뒤) | 문법 오류 없음 (Python `ast` · JavaScript tree-sitter) | 부분 수정 |
| 1 | 코드가 비어 있지 않고 300줄 이하 | 다시 만들기 |
| 2 (검토 뒤) | 코드의 함수·반복문이 모두 어느 흐름 단위 안에 들어 있음 | 빠진 곳을 알려 주고 검토 1번 더 |
| 2 | 반복·재귀 단위에 `count`·`stop` 이 있음, 모든 단위에 모범 설명이 있음(300자 이하) | 검토 1번 더 |
| 2 | 손으로 따라갈 크기 (3.1 오른쪽 선): 반복 단위의 `count` · `output` 줄 수 | 데이터·반복을 줄이도록 부분 수정 → ② 다시, 아니면 ① 다시 |
| 2 | 설명할 곳(`key`) 1곳 이상 (없으면 함수·반복 단위를 서버가 고름, 최대 5곳 · 겹치면 바깥 것 하나만) | 고치고 넘어감 |
| 판정 | `runnable=false` 또는 `problems` 있음 | 부분 수정 → ② 다시 |
| 판정 | `level.match=false` | `advice` 를 붙여 ① 다시 |

## 6. 실패 처리

| 상황 | 처리 |
|---|---|
| 문법 오류 · 동작하지 않음 · 따라가기에 너무 큼 | 줄 번호를 붙인 코드와 문제를 주고 **바꿀 줄만** 받기 (`code_fix`, 문항당 1번 — 너무 크면 데이터 개수·반복 횟수를 줄이게) → 다시 검사 |
| 난이도 불일치 | 검토의 `advice` 와 지금 코드를 주고 ① 다시 (1번) |
| 그래도 걸림 · AI 호출 한도(6번) · AI 를 쓸 수 없음 | 같은 언어·난이도의 **예시 코드** (`samples.py`, `npm run verify` 가 실제 실행으로 확인) |
| 검토 AI 답의 형식 오류 | 빠진 칸을 알려 주고 1번 더 묻기(`ai.py`). 그래도 틀리면 다시 만들기 — **검토를 거치지 않은 코드는 내보내지 않아요** |

## 7. 채점 기준 (`jojo_review`)

학습자는 코드에 형광펜으로 줄 범위를 고르고 흐름을 설명하는 메모를 써요. 채점은 **검토 AI 의 실행 기록**을 기준으로 해요.

- 메모와 겹치는 흐름 단위의 `inputs`·`steps`·`result`·`count`·`stop`·`explanation` 을 채점 AI 에게 기준으로 줘요
- 판정은 **흐름을 이해했는지**로: ○ 순서·조건·결과의 의미가 맞음 (숫자가 조금 달라도) · △ 큰 흐름은 맞지만 중요한 조건·순서가 빠짐 · ✕ 흐름을 다르게 이해함
- ⬚ 빈칸: 설명할 곳(`key`) 중 메모가 하나도 겹치지 않은 곳 (규칙)
- 첨삭 문장은 정답을 바로 주지 않고 다시 볼 줄·조건을 짚어요. 결과 화면에 모범 설명과 실행 기록을 보여 줘요
- 채점 AI 를 쓸 수 없으면 핵심 표현이 메모에 들어 있는 비율로 규칙 채점

## 8. 생성 기록으로 배우기 (`history.py`)

코드를 하나 만들 때마다 **성공·실패를 모두 기록**하고, 다음에 같은 언어·난이도로 만들 때 최근 기록을 읽어 생성 AI 에게 지침으로 줘요 (RAG 처럼 — 검색은 DynamoDB 조회 한 번, AI 없음).

| 단계 | 내용 |
|---|---|
| 기록 | `GENLOG#<언어>#<난이도>` / `<시각>` (180일): 주제 · 결과(AI 제공 / 예시 코드) · 시도마다 결과 분류와 짧은 이유 · 통과한 코드의 **모양**(줄 수 · 함수 수 · 반복문 수 · 출력 줄 · 검토가 본 난이도). **코드 원문은 저장하지 않아요** |
| 분류 | `ok` 통과 · `rule` 문법·오타 · `not_runnable` 동작하지 않음 · `too_big` 따라가기에 너무 큼 · `level_up`/`level_down` 요청보다 어렵다/쉽다고 판정 · `disagree` 두 AI 기록이 다름 · `review_error`·`check_error`·`unavailable` AI 를 못 씀 (지침에는 쓰지 않음) |
| 읽기 | 만들기 전에 같은 언어·난이도의 최근 40개 (5개보다 적으면 쓰지 않음) |
| 지침 1 | 자주 걸린 분류(2번 이상 · 시도의 15% 이상, 많은 순 3개)마다 정해 둔 "이렇게 하지 마세요" 문장 |
| 지침 2 | 통과한 코드의 모양(중앙값): "약 L줄 · 함수 F개 · 반복문 R개 · 출력 O줄 — 크기·구조만 참고하고 주제·구성은 새롭게" |
| 다양성 | 코드 원문을 주지 않아 같은 코드가 반복되지 않아요. 주제는 지금처럼 최근에 쓴 것을 빼고 골라요 |
| 끄기 | 환경 변수 `HISTORY_HINTS=off` 면 지침을 주지 않아요 (기록은 계속). 켜고 끈 실험으로 효과를 비교해요 |
